## Vibe coding versus engineering

The difference isn't whether a model wrote the code. It's whether anyone can say why the
code is the way it is, what was checked before it shipped, and what would have stopped it if
it were wrong. Vibe coding is accepting output. Engineering is owning it.

Everything below exists to make ownership possible at a speed one person couldn't otherwise
sustain.

## Rules that load themselves

The repo carries a top-level rules file every session reads, plus path-scoped rules that
auto-load when a session opens a matching file: touch channel code and the "master is
sacred" rule appears; open a deploy workflow and the pipeline's gotchas appear. Area docs —
inventory, shipping, finance, jobs — hold the invariants and the incident ledger for that
area.

The point is that a session doesn't have to *remember* to read the rules. The rules find it.

## Hooks that say no

Advice gets ignored under time pressure, by humans and agents alike. So the operations that
have caused incidents are blocked, not discouraged:

- `git add -A`, `git commit -a`, `--no-verify` — blocked by a pre-tool hook. Staging by
  explicit path is the only path, because the git index is shared and a broad add sweeps
  another session's work into your commit.
- Broad Jest runs — blocked. Scoped suites only. The full lanes run in CI on every push,
  where they can't take down the machine ten sessions share.
- A commit in a checkout where another session is mid-commit — blocked until they finish.

Each block prints the reason and the sanctioned alternative. A subagent that never read the
rules is stopped the same way, which is the whole point.

## Knowing who else is here

A coordination layer registers every session at start, tells it who else is live, and whether
any of them share the same checkout. Sessions can broadcast a finding to the others. By
default a session works in its own git worktree, branched fresh from the integration branch,
so parallel work never touches the same index at all.

<Takeaway>
  The failure ledger for this system is public inside the repo — every incident, its cost,
  and the constraint it produced. Reading it is how a new session, or a new engineer,
  learns why the rules are shaped the way they are.
</Takeaway>

## Review by consequence

Not every change deserves a second opinion, and reviewing everything trains everyone to skim.
The rule: a second-model review is triggered by what a mistake would *cost*, not by how many
lines changed. Money, books, bulk writes to production data, writes to a vendor's API,
migrations, permissions, and anything that can be *silently* wrong — reviewed before
executing, by a different model than the one that wrote it. UI, copy, layout, read-only
reports — ship on sight; a wrong pixel is not a wrong ledger.

## Verify before you assert

The last rule is the one I'd keep if I could only keep one. Nothing is "done", "fixed" or
"passing" without the verification output behind it. Run the query. Curl the endpoint.
Screenshot the page. "It's probably fine" after five minutes of reasoning is worth less than
one command that shows what it really is — and it's how confidently-wrong work ships.

That rule applies to me as much as to the agents. It's the part of the job that hasn't
changed.
